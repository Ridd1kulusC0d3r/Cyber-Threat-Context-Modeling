# TCE Principles

These principles define the project beyond any single framework.

1. **Mission before matrix.** Start with what the organization must protect, not with a technique catalog.
2. **Crown jewels are relationships, not labels.** A critical asset is only meaningful in the context of the process, identity, dependency, and impact around it.
3. **Architecture is adversary terrain.** Trust boundaries, control planes, identities, and dependencies shape feasible attack paths.
4. **Theory and evidence are complementary.** Public reporting tells us what has happened; modeling helps us reason about what could happen.
5. **Priority is not confidence.** High-impact low-confidence scenarios still deserve explicit treatment.
6. **Sequence beats alert count.** Multi-stage behavior often has more meaning than isolated suspicious events.
7. **Telemetry is designed.** Required observations are security requirements, not whatever happens to arrive in the SIEM.
8. **Detection is a hypothesis.** Rules are implementations of a behavioral claim that must be testable.
9. **Defenses must alter attack paths.** Controls should prevent, constrain, expose, disrupt, or accelerate recovery from modeled behavior.
10. **Validation closes the loop.** Coverage without testing is an assertion.
11. **The detection stack is part of the threat model.** Loss of visibility, pipeline failure, and rule tampering are themselves security risks.
12. **CTI must change a decision.** Intelligence that never changes priority, architecture, telemetry, detection, or validation is context-free reading.
13. **Models age.** Every artifact needs an owner, evidence date, and review trigger.
14. **Interoperability over framework loyalty.** ATT&CK, D3FEND, NIST, STRIDE, PASTA, Attack Trees, and other methods are lenses, not religions.
15. **Operational outputs over diagram theater.** The deliverable must create work that a security team can execute.
